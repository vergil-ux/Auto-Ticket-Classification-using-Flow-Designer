# Project Demonstration Phase

Here's roughly how I'd walk someone through this project live — this is the order I'd actually click through things in a demo.

## 1. Set the scene (30 seconds or so)

Quick explanation before touching the instance: the school IT helpdesk gets the same handful of issue types every day — Wi-Fi, projectors, passwords, slow computers — and right now a human has to read every single ticket just to figure out which bucket it belongs in. This project automates that one step.

## 2. Show the table

Open the `Incident WorkFlow` table and walk through the fields — Caller, Category, Subcategory, Short Description, State, etc. Point out that Category and Subcategory are dependent choice fields, so picking one filters the other.

## 3. Create a ticket live — Wi-Fi example

- Open a new record on Incident WorkFlow.
- Fill in a Caller name.
- Type into Short Description: `WiFi not working in library`
- Leave Category and Subcategory blank.
- Save.
- Reload the form.

**What should happen:** Category flips to `Network`, Subcategory flips to `Wi-Fi`, with no one touching either field.

## 4. Show the email went out

- Navigate to **System Logs → Emails**.
- Search for the subject line configured in the flow.
- Open the record and click **Preview Mail** under Related Links to show exactly what the caller received.

## 5. Second example — Projector

- Create another ticket: `Projector not turning on`
- Save and reload.
- Show Category = `Hardware`, Subcategory = `Projector`.

This second example is useful for showing the audience it's not a one-off fluke — the same logic reliably branches to a different category based on different keywords.

## 6. Peek under the hood

- Open Flow Designer and pull up `Auto Classify School IT Tickets`.
- Walk through the trigger (Record Created on Incident WorkFlow, Category is empty).
- Walk through the If/Else If chain, showing how each branch checks for a keyword and updates the record.
- Show the Send Email action at the end.

This is usually the part that lands best in a demo — people can see, in plain English, exactly why a ticket got classified the way it did. Nothing hidden in a model somewhere.

## 7. Be upfront about the limits

- If a caller phrases their issue in a way that doesn't match any of the current keywords, the ticket stays uncategorized rather than falling into some generic bucket — worth mentioning as a known trade-off of the keyword approach, and an easy thing to improve later.
- It's a small, focused solution built for a small, predictable set of issue types — not meant to replace a full enterprise ticketing/classification system.

## 8. Close it out

The project takes one repetitive manual task — categorizing incoming tickets — and automates it with a simple, transparent Flow Designer setup, no scripting or machine learning involved. It's easy to extend (new keyword, new category) and easy for someone else to pick up and maintain, which for a small school IT setup matters more than a fancier but harder-to-maintain ML solution would.
