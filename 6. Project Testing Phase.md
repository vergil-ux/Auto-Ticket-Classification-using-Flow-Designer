# Project Testing Phase

The goal here was pretty simple: make sure the flow actually classifies tickets correctly and that the confirmation email really goes out — and along the way, check that the data being stored is clean and that access to it is reasonably locked down.

## Data validation checks

Before diving into scenario testing, I confirmed the basics:

- Mandatory fields (Caller, Short Description) are actually being captured.
- The auto-number on new records generates correctly with no duplicates.
- Category and Subcategory values are being stored exactly as expected, not left blank or mismatched.
- Reference fields (Caller, Assigned Group, Assigned To) correctly resolve to real user/group records instead of showing broken references.

## Test scenario 1: Wi-Fi ticket

**What I did:**
- Entered a Caller name.
- Set Short Description to: `WiFi not working in library`
- Saved the form, then reloaded it.

**Result:**
- Category auto-filled to `Network`
- Subcategory auto-filled to `Wi-Fi`
- A confirmation email was sent to the caller's email address

This one worked exactly as expected on the first try.

## Checking the email actually sent

To confirm the notification wasn't just theoretically configured but actually firing:

1. Went to **All menus** → searched **Emails**.
2. Under **System Logs**, opened **Emails**.
3. Searched using the subject line I'd set in the flow.
4. Opened the matching record and, under **Related Links**, clicked **Preview Mail** to see exactly what the caller would have received.

Confirmed the subject and body matched what I'd configured in the Send Email action.

## Test scenario 2: Projector ticket

**What I did:**
- Entered a Caller name.
- Set Short Description to: `Projector not turning on`
- Saved and reloaded the form.

**Result:**
- Category auto-filled to `Hardware`
- Subcategory auto-filled to `Projector`
- Email sent to the caller's mail ID, confirmed the same way as above.

## What I'd still want to test with more time

- Phrasing that doesn't match any of the current keywords (e.g., "internet is down" instead of "WiFi") — as expected, this leaves Category empty since there's no fallback branch. Noted as a known limitation rather than a bug.
- Mixed-keyword short descriptions (e.g., a description that happens to mention both "Wi-Fi" and "Slow") — worth checking which branch wins given the If/Else If order.
- Basic access control — confirming only appropriate roles can view/edit records on the Incident WorkFlow table, since it holds caller information.

## Outcome

Both keyword scenarios I tested classified correctly and triggered the email exactly as designed. The dependent choice fields also behaved correctly — the Subcategory options shown lined up with whatever Category the flow had just set. Nothing broke, and I didn't need to go back and rework any of the branch logic.
