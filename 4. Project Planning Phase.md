# Project Planning Phase

## How I broke the work down

I split the project into five working phases, roughly in the order I actually built things — each one building on the last:

1. **Requirement Analysis & Planning** – nail down what the system needs to do, set up the Update Set.
2. **Backend Development & Configuration** – build the custom table, fields, and the Category/Subcategory dependency.
3. **Automation (Flow Designer + Email)** – the actual classification logic and the confirmation email.
4. **Testing, Validation & Security** – make sure it actually works and doesn't leak data it shouldn't.
5. **Deployment & Final Documentation** – package everything into the Update Set and write it all up.

## Rough timeline

| Phase | What I was doing |
|---|---|
| Requirement Analysis & Planning | Defined the business requirements, created the Update Set |
| Backend Development & Configuration | Built the Incident WorkFlow table, added fields, set up dependent choices |
| Automation via Flow Designer | Built the trigger, the If/Else If keyword logic, and the email action |
| Testing, Validation & Security | Ran test tickets through the flow, checked the emails actually went out |
| Deployment & Final Documentation | Marked the Update Set complete, exported it, wrote up the docs |

## Tools I used

- ServiceNow instance (PDI)
- Flow Designer (Process Automation)
- System Definition → Tables (for the custom table)
- System Update Sets (for packaging the work)
- System Logs → Emails (for verifying notifications during testing)

## Things I flagged as risks going in

- **Keyword matching is only as good as the wording** — if a caller writes something like "internet down" instead of "Wi-Fi", the flow won't catch it because there's no keyword for that phrasing. This is the main trade-off of going keyword-based instead of ML-based, and it's worth being upfront about.
- **No fallback category** — as designed, the trigger only fires when Category is empty, and if none of the If/Else If branches match, the ticket just stays uncategorized rather than falling into some default "Other" bucket. Something to improve later.
- **Single Update Set** — since everything (table, fields, flow) lives in one Update Set, I had to be careful about the order I built things in, since a flow referencing a field that isn't captured yet can cause issues on import elsewhere.

## What "done" looks like

- A ticket submitted with just a Caller and Short Description gets Category + Subcategory filled in automatically, with no manual step.
- The caller receives a confirmation email right after submitting.
- The Update Set is complete and exportable, so the whole thing can be moved to another instance.
