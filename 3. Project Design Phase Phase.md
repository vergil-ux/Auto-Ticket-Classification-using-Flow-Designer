# Project Design Phase

> Keeping the file name exactly as requested ("Design Phase Phase") — I'm guessing it's a typo in the original phase list, but I left it as-is so it matches what was asked for.

## Designing the data structure

Before touching Flow Designer, I needed somewhere to actually store these tickets. Rather than reuse the standard Incident table with a bunch of unrelated fields, I designed a dedicated custom table called **Incident WorkFlow** so I had full control over the fields and choices relevant to this project.

## Fields I planned out

| Field Label | Type | Reference / Choice |
|---|---|---|
| Number | Auto Number | — |
| Caller | Reference | `sys_user` |
| Category | Choice | Network, Hardware, Access, Performance |
| Subcategory | Choice | Wi-Fi, Projector, Forgot Password, Slow Computer |
| Short Description | String | — |
| Description | String | — |
| State | Choice | New, In Progress, On Hold, Resolved, Closed |
| Assigned Group | Reference | `sys_user_group` |
| Assigned To | Reference | `sys_user` |

I kept the field list intentionally small. The whole point of this project is a lightweight, no-code classification layer — there was no reason to drag in every field the base Incident table has.

## Designing the Category → Subcategory relationship

This part needed a bit more thought. Category and Subcategory can't just be two independent choice lists — if someone picks "Network" as the Category, the Subcategory dropdown shouldn't be showing "Projector" as an option. So I designed these as **dependent choice fields**, where Subcategory is dependent on whatever Category was set.

The mapping I designed:

| Category | Subcategory |
|---|---|
| Network | Wi-Fi |
| Hardware | Projector |
| Access | Forgot Password |
| Performance | Slow Computer |

Since Category is going to be set automatically by the flow anyway (not picked by a human), this dependency is really there to keep the data clean and to make the form sensible if anyone ever needs to review/edit a ticket manually.

## Designing the classification logic

Rather than anything ML-based, the classification design is a simple, readable rule set based on keywords appearing in the Short Description:

- Contains **"Wi-Fi"** or **"Network"** → Category = Network, Subcategory = Wi-Fi
- Contains **"Projector"** → Category = Hardware, Subcategory = Projector
- Contains **"Password"** or **"Login"** → Category = Access, Subcategory = Forgot Password
- Contains **"Slow"** or **"Hanging"** → Category = Performance, Subcategory = Slow Computer

This maps cleanly onto Flow Designer's **If / Else If** branching, which is exactly how I designed the flow to be structured — one condition block per keyword group, each ending in an "Update Record" action.

## Designing the notification step

Once a ticket is classified, the design calls for an automatic email back to the caller confirming their request has been logged — so from the caller's side, nothing changes about how they raise a ticket, they just get a reply almost immediately instead of silence.

## Why I designed it this way

- **Dependent choice fields** keep Category/Subcategory combinations valid and prevent nonsensical pairings.
- **Keyword-based If/Else If logic** is transparent — anyone opening the flow later can read it top to bottom and understand exactly why a ticket got classified the way it did, no black box.
- **A dedicated custom table** kept the project self-contained and easy to demo without touching the org's live Incident table.
