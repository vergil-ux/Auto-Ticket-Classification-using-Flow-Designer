# Requirement Analysis Phase

## Background

The school IT helpdesk receives multiple support requests daily from students and teachers related to common issues such as network connectivity, hardware failures, account access problems, and system performance issues.

Right now, IT staff manually review each ticket to:

- Identify the issue type.
- Select the correct category and subcategory.
- Inform the caller that the ticket has been created.

This manual process is time-consuming, error-prone, and doesn't scale well as the number of requests grows. That's the gap this project is meant to close.

## Business use case

A student or teacher raises a support request describing their problem in plain language. Instead of an IT agent having to read it and manually decide on a category, the system should figure that out on its own based on the words used in the description, and let the caller know their request has been received — all without any extra effort from either side.

## Business requirements

Based on that use case, the system needs to:

- Automatically classify IT tickets based on the issue description.
- Assign both **Category** and **Subcategory** without manual intervention.
- Support dependent choice logic between Category and Subcategory (so the Subcategory options make sense for the selected Category).
- Send an automated email notification to the caller upon ticket creation.
- Store ticket information in a structured, standardized format.
- Be easy to maintain and extend as new issue types come up.

## Setting up the workspace: creating the Update Set

Before building anything, I set up a dedicated Update Set so all the changes for this project (tables, fields, flow, everything) stay bundled together and can be moved/exported cleanly at the end.

**Steps I followed:**

1. Went to **All menus** → searched for **Update Set**.
2. Under **System Update Sets**, opened **Local Update Sets**.
3. Clicked **New** in the top right.
4. Filled in:
   - Name: `Project Update Set`
   - State: `In Progress`
   - Application: `Global`
5. Saved the form.
6. Under **Related Links**, clicked **Make This My Current Set**.
7. Confirmed the Update Set now showed up as my current/active set at the top of the instance.

Everything I built after this point — the custom table, the fields, the flow — was captured inside this Update Set, which made it much easier to package up for deployment later.

## Summary

At the end of this phase I had a clear list of what the system needed to do, and a clean Update Set ready to capture the build. Next step was designing the actual data structure that would hold these tickets.
